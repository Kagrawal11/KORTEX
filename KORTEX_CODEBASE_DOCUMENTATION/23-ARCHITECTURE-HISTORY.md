# 23 — Architecture / Evolution History

## A note on method, before anything else

**Git history for this repository does not describe the current codebase and should not be trusted as an evolution record.** Verified directly: `git log --oneline` returns roughly 10 commits, the last of substance titled *"added features and fixed backend DIR to use Backend_FIXED_v2 and Frontend_FIXED_v2."* `git status` at the start of this documentation effort showed the **entire** current `backend/` and `frontend_FIXED_v2/frontend/` implementation — every entity, controller, service, and page described anywhere in this documentation set, including all of API Testing, Accessibility, PDF/Email reporting, the Dashboard, and every Data-Driven/Playback robustness fix — sitting as uncommitted working-tree changes against an older `backend_FIXED_v2` layout that git still remembers as the prior state. None of this work is captured in any commit message. A commit-by-commit feature timeline simply does not exist to reconstruct.

What *does* exist, and what this document is built from instead, is a rich trail of evolution evidence **left inside the source itself**: inline comments that say "previously X, now Y," "confirmed on a real run," "BUG FIX:," and dedicated test-file section comments that narrate the exact production failure a piece of logic was written to fix. This is unusually good self-documenting history for a codebase — better, in places, than git log would have been — and it's what every claim below is grounded in.

---

## 1. The earliest layer: UI Automation (record & playback)

The foundational domain model — `TestScenarioEntity` → `TestStepEntity`, `TestRunEntity` → `TestRunStepEntity` — and the core `RecordingSession` / `EventListenerInjector` / `PlaybackEngine` trio are the oldest working parts of the system. Evidence: every other feature's entities and services either depend on this layer (Data-Driven executes the *same* `TestStepEntity` rows recorded here) or were built alongside it using its established conventions (JSON-text-column storage for structured detail, `System.out.println` bracket-tag logging, the request→controller→service→repository layering).

Within this layer, the selector-generation and selector-resolution logic shows the clearest internal evolution trail:

- **Selector generation** (`EventListenerInjector.java`) accumulated a *specific, named* exclusion list for "volatile" generated ids over time — jQuery UI's `ui-id-N`, React's `useId()` guillemet/colon forms, bare UUIDs, purely-numeric ids, and known component-library prefixes (MUI/Radix/Headless UI/Ember/react-select). The code's own comment records that a generic "ends in digits" heuristic was considered and *rejected* because it false-positived on legitimate hand-authored ids like `section2` — each pattern instead targets a shape real generated ids actually take. This is iteration driven by real recordings against real sites, not a from-scratch design.
- **Positional selector fallback** was rewritten from a bare `tag:nth-of-type(idx)` (matched *any* element anywhere in the document satisfying that shape — confirmed to have once resolved to an unrelated `<div class="aspNetHidden">` on a real ICICI order form) to a bounded 4-level ancestor chain scoped with `>` combinators, anchoring to a stable id early if one is found.
- **Button-like `<input>` handling** was added specifically because the positional fallback, for a `<input type="submit">` with no id/name, once matched "the first button-type input in whatever document is loaded" — which played back as clicking `btnOAOSiteLogin` (value="Login") and navigated the whole session away. The fix anchors on the input's `value` attribute instead.

## 2. Playback hardening: navigation, dropdowns, self-healing

`PlaybackEngine.java` is the largest and most-evolved file in the codebase. Its own comments narrate several distinct hardening passes:

- **Positional-selector-shape false positives.** `isInputStep()`'s click-branch (shared conceptually with `FieldMappingService`, see below) originally matched any click whose selector/label/placeholder merely *contained* the word "select" — misclassifying an ordinary "Select Plan" button as a mappable dropdown field. Tightened to require an ARIA `role="option"` or a specific set of recognized dropdown/listbox selector shapes.
- **Dropdown overlay timing.** `isDropdownOverlayOpen()` and the short fixed-wait branch it enables exist because a long NETWORKIDLE-style wait after opening a dropdown would let the overlay close again before the next step could act on it — the fix recognizes a specific, growing list of overlay-panel selector shapes (PrimeNG panels, ARIA listbox, flatpickr/date-picker panels) and uses a short fixed sleep instead.
- **Dropdown-option override rewriting** (`cloneWithOverride()`) originally only handled a narrow PrimeNG-specific selector pattern; every other dropdown flavor (native `<select>`, Angular Material, Bootstrap, plain ARIA listboxes) fell through to reusing the *originally recorded* option, silently replaying the same value on every data-driven row regardless of that row's actual mapped data. The fix builds a comma-joined, content-scoped selector list covering all of these shapes at once.
- **This session's fix — dropdown verification + reopen-on-retry.** A real run against `gmsuat.cgtmse.in` showed a dropdown-option override click could close the option list without actually selecting the mapped value (the list hadn't finished rendering when the click cascade fired). `verifyDropdownOverrideSelection()` was added to catch this (checking both "did the overlay close" and "is the mapped value now visible anywhere on the page"), with one retry. The retry initially just re-searched the same (now-closed) option list and was certain to fail; the same-session follow-up fix added a `reopenTriggerStep` parameter so the retry can re-click the dropdown's own trigger step to reopen the list before trying again — only when the overlay is confirmed closed, so it doesn't fight a genuinely-still-open list.
- **Self-healing terminology gap (documented, not fixed).** `StepStatus.HEALED_BY_AI` fires for *any* successful fallback past the primary selector — including fully deterministic id/name/label matches — not only genuine LLM calls. This predates the current documentation effort and was confirmed, not introduced, during this pass (see `22-LIMITATIONS.md`).

## 3. Data-Driven testing: four narrated rounds of the same underlying problem

`backend/src/test/java/com/miniautomation/backend/datadriven/FieldMappingServiceTest.java` is unusually good verified history — its own section comments narrate four distinct real-world rounds of the identical logical bug (*"a dropdown option step isn't recognized as a mappable field"*), each caused by a different site rendering the same conceptual widget slightly differently, and each fix broadening the detection net without discarding the previous fix:

1. **Round 1 — the baseline.** A click-based dropdown OPTION step (e.g. the actual cancellation reason clicked in a list) has no labelText/name/id/placeholder of its own — only the sample value chosen during recording. `findPrecedingDescriptiveText()` was added: look at the nearest preceding step's own recorded text (very often the dropdown's own opening trigger, e.g. "Select Cancellation Reason") as a stand-in label and, when it happens to equal a dataset column name, a genuine auto-match.
2. **Round 2 — recorded as a plain `<span>`, not a real ARIA option.** A second real recording of the *identical logical action* captured the option as a bare `<span>` with `role="span"`, not `role="option"` — indistinguishable from a genuinely fixed, always-the-same menu click by structure alone. `isColumnDrivenCandidate()` was added: anchor to the dataset's own column names instead of guessing from element structure — if the nearest preceding step's text matches a real column header, the step immediately after it is almost certainly that column's per-row value.
3. **Round 3 — even the trigger's text came back blank.** A third recording captured the dropdown trigger click with *no* text at all (the click landed on an icon/arrow inside the trigger with empty `innerText`), so round 2's "preceding step's text" signal had nothing to work with. `valueMatchedColumn()` was added: match the option step's own recorded sample text directly against actual dataset **cell values** (not header names) — a signal that needs nothing from any other step.
4. **Round 4 — this session, the "CGT RE" recording.** A fourth recording, against the same real site, exposed two compounding gaps at once: (a) `isInputStep()`'s structural check didn't recognize PrimeNG's real, unhyphenated custom element tag `<p-dropdownitem>` (the existing check only matched hyphenated CSS-class forms like `.p-dropdown-item`) — fixed by adding the unhyphenated tag-name patterns for the whole PrimeNG option-bearing widget family (Dropdown/MultiSelect/Listbox/SelectItem). (b) `findPrecedingDescriptiveText()` would walk back past a blank-text immediate predecessor to *any* earlier step with non-blank text, however distant and unrelated — which is actively unsafe, not merely incomplete, since a coincidental match to an unrelated step's text could produce a *wrong* silent auto-match rather than no match at all. Fixed by restricting the lookup to the single immediate predecessor (falling back to that same step's labelText/ariaLabel/placeholder before giving up), rather than reaching further back.

**Known incomplete state as of this documentation**: `frontend_FIXED_v2/frontend/src/components/DataDrivenPanel.tsx` contains a hand-maintained mirror of this exact backend logic (explicitly commented "Mirrors FieldMappingService.X on the backend EXACTLY," acknowledging in its own comments that the two have diverged once before and must be kept in sync deliberately). As of this documentation pass, the frontend mirror has **not** received Round 4's two fixes — see `18-CROSS-MODULE-CONNECTIONS.md` and `22-LIMITATIONS.md` for the live consequence.

The same session also hardened `DataDrivenExecutionService.executeLoopRow()`: a real run showed `getColumnForStep()` was gated behind `isInputStep()`, silently discarding a valid mapping (reached only via the broader Round 2/3 signals) at *execution* time even though the mapping screen had correctly offered and validated it — the step then replayed its originally recorded value on every row with no error. The lookup is now unconditional.

## 4. Accessibility scanning — a later, self-contained addition

Accessibility scanning was added as an architecturally separate feature: its own isolated Playwright/browser session (not `BrowserManager`), its own entity pair (`AccessibilityScanEntity`/`AccessibilityScanRunEntity`), its own async executor. It integrates with the axe-core engine for a single-page, single-load scan — no crawling, no interaction-state simulation. A manual/guided testing checklist was layered on afterward as a hybrid design (static question definitions in the frontend, answers persisted backend-side) to cover the class of accessibility issue axe-core cannot detect automatically (see `08-ACCESSIBILITY.md` for what's covered vs. not).

## 5. API Testing — the newest major module

API Testing is the most recently built first-class feature, added deliberately reusing this codebase's existing Playwright dependency (via `APIRequestContext`, an HTTP-only execution mode with no browser page) rather than introducing a second HTTP client library — matching the explicit direction that shaped its design. Its domain model (Collection → Folder → Request, Environment/Variables, structured JSON-column sub-config for params/headers/body/auth/assertions) follows the same "rich structured detail as a JSON text column" convention already established by `TestStepEntity` and other earlier entities, rather than inventing a new persistence pattern.

Real bugs found only through live end-to-end testing during this feature's build (not design-time reasoning) shaped several of its current behaviors:
- A `LazyInitializationException` on `GET /api/api-testing/collections` led to the now-standard EAGER-fetch-plus-`@JsonIgnoreProperties` pattern being applied to `ApiFolderEntity`/`ApiRequestEntity`'s `collection`/`folder` relations.
- The persisted `resolvedUrl` was found to silently drop query parameters (including ones injected by API-key-in-query auth) because they were sent to Playwright separately via `RequestOptions.setQueryParam()` but never appended to the stored/displayed URL string — fixed by building the URL's query string explicitly before persisting.
- The frontend's `startRun()` originally wrapped its multipart `config` field in a `Blob`, which browsers send as a file-like part with an implicit filename — breaking Spring's plain-`String` `@RequestParam` binding as a silent 500 with no stack trace. Fixed by matching the already-proven plain-string pattern used by the Data-Driven feature's own `startRun()`.

API Testing's own report/PDF/email integration and its inclusion in the shared Dashboard/Execution History aggregation were both added as follow-on work once the execution engine itself was stable — see the Dashboard note below for a gap that follow-on work left behind.

## 6. PDF + Email reporting — evolved alongside each feature, not built once

`ReportPdfService` did not gain all four report types (Standard/Data-Driven/Accessibility/API Testing) at once — each `generateXxxPdf()` method was added as its corresponding feature matured, on the same underlying openhtmltopdf renderer. One concrete compatibility fix surfaced this way: `word-break: break-all` (used in an early attempt at wrapping long resolved API URLs) is not a supported CSS property in openhtmltopdf and had to be removed after a build-time warning surfaced it.

## 7. Dashboard / Execution History — the aggregation layer arrived after the features it aggregates

`DashboardService` was necessarily one of the later additions, since it reads from every other feature's repositories. Its `getAllRuns()` method returns flat per-kind DTOs rather than raw entities specifically because `DataDrivenRunEntity.scenario` lacks the `@JsonIgnoreProperties` trimming that `TestRunEntity.scenario` already had — serializing it raw in a list would have embedded every row's full `scenario.steps` array. This is a real, verified inconsistency in how different entities across the codebase handle JSON serialization, not a deliberate design choice documented anywhere in source.

**Known incomplete state as of this documentation**: `getSummary()` (the top Dashboard stats) was not updated when Accessibility and API Testing were added — it still aggregates only UI Automation and Data-Driven runs. `getAllRuns()` (Execution History) *was* updated to include all four kinds. This is the clearest evidence in the whole codebase that the Dashboard's top-stats aggregation and the Execution History aggregation evolved on separate, imperfectly-synchronized tracks even though they're computed by the same service class.

## 8. What this evolution pattern predicts about the codebase's current risk areas

Reading these histories together, one pattern recurs across every module: **a new real recording, a new real site, or a new feature addition tends to surface a gap in whatever the *previous* feature's hand-written heuristics assumed** — and the fix is consistently to broaden detection with an additional, narrowly-scoped signal rather than to rewrite the whole mechanism. This is a deliberate, conservative engineering style (visible in explicit code comments rejecting broader/looser heuristics in favor of narrower, evidence-anchored ones), and it means:

- Any place with a **hand-mirrored copy of logic across two layers** (frontend/backend, as with `DataDrivenPanel.tsx`/`FieldMappingService.java`) is a predictable place for exactly this kind of drift to recur — there is no shared-code or code-generation mechanism preventing it.
- Any **aggregation service that reads from multiple feature repositories** (`DashboardService`) is a predictable place for a newly-added feature to be missed in one aggregation path while correctly wired into another, as happened with Accessibility and API Testing in `getSummary()`.
- The self-documenting comment style throughout this codebase (explaining *why*, with a real failure narrative, not just *what*) is itself a maintained convention — new work should continue it, since it is what made this history document possible to write accurately at all.
