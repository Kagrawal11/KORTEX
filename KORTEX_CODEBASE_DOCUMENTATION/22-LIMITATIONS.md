# 22 — Known Limitations / Risks

Every item below was verified against source during this documentation pass (either directly, or via one of the round-1 documents, each cited). Nothing here is speculative padding — this document follows the same rule as the rest of the set: **Known limitation** means confirmed current behavior; **Potential risk** means a plausible, clearly-labeled consequence of a known limitation, not an observed failure; **Not verified** means a round-1 document flagged something it could not confirm either way. Nothing is invented beyond what these three labels justify.

---

## Security

- **Known limitation — plaintext database credential committed to the repository.** `backend/src/main/resources/application.properties` contains a real value for `spring.datasource.password`, and the file is tracked by git. This documentation withholds the value everywhere (see `15-CONFIGURATION.md`); it was also flagged directly to the user outside this documentation deliverable, since it warrants action independent of any doc. **Potential risk:** if this repository is ever pushed to a shared or public remote, the credential is recoverable from git history even after the file is edited — rotating the credential is the only complete remediation once that happens.
- **Known limitation — no authentication or authorization anywhere in the backend.** No Spring Security dependency exists (`02-ARCHITECTURE.md`, `15-CONFIGURATION.md`). Every REST endpoint on every controller is open to anyone who can reach the port. **Not verified**: whether any reverse proxy or hosting layer in front of this backend adds auth — nothing in this repository does.
- **Known limitation — every controller allows all origins.** `@CrossOrigin(origins = "*")` is applied individually on 9 of the 10 controllers (`02-ARCHITECTURE.md`). Combined with no auth, any web page loaded in a browser that can reach the backend's host/port can call every endpoint, including starting a real browser-driven test run or accessibility scan against an arbitrary URL.
- **Known limitation — no host allowlist anywhere in the app.** Recording/playback, accessibility scanning, and API Testing's HTTP executor will all navigate to or call any URL the user supplies, including internal/staging/localhost addresses (`08-ACCESSIBILITY.md` §3 confirms this is a deliberate, explicit design choice for accessibility scanning specifically — no blocklist). `ApiHttpExecutor` also sets `ignoreHTTPSErrors(true)` unconditionally, so self-signed/expired TLS certs are silently accepted (`09-API-TESTING.md` §2).
- **Known limitation — secret masking has no second layer at report time.** API Testing masks secret values before persisting them, but `ReportPdfService` performs no masking of its own — it renders whatever the entity already contains (`12-REPORT-PDF-EMAIL.md` §4.7). **Potential risk:** any future change to the execution engine that stores an unmasked secret would flow into generated PDFs and emails with no independent safety net catching it.

## Database

- **Known limitation — no `@Transactional` boundary anywhere in the backend** (`10-DATABASE.md` §0, confirmed by an exhaustive grep returning zero matches). Every multi-entity write relies entirely on JPA cascade within a single `.save()` call, not an explicit transaction. **Potential risk:** a mid-run crash between accumulating results and the single final `.save()` call (e.g. in `DataDrivenAsyncExecutor`, `ApiRunAsyncExecutor`) loses all in-progress results for that run — there is no incremental/per-row persistence (`10-DATABASE.md` §3.1 states this explicitly for the Data-Driven case).
- **Known limitation — no database indexes beyond primary keys and implicit foreign-key indexes.** No `@Index`/`@Table(indexes=...)` annotation exists on any entity (`10-DATABASE.md` §0). **Potential risk:** query performance would degrade as run/history tables grow, particularly for `DashboardService`'s `findAll()`-then-aggregate-in-memory pattern (`13-DASHBOARD-HISTORY.md` §1), which has no pagination or filtering pushed to SQL at all.
- **Known limitation — almost nothing can be deleted.** Only the API Testing collection/folder/request/environment family has delete endpoints. `TestScenarioEntity`, `TestRunEntity`, `DataDrivenRunEntity`, `AccessibilityScanEntity`/`AccessibilityScanRunEntity`, and `ApiRunEntity` have no delete path anywhere in the backend (`10-DATABASE.md`, `11-API-ENDPOINTS.md` §9). Test/run/scan history accumulates permanently.
- **Known limitation — schema is Hibernate-auto-managed, not migration-controlled.** `spring.jpa.hibernate.ddl-auto=update`, no Flyway/Liquibase dependency (`10-DATABASE.md` §0, `15-CONFIGURATION.md`). There is no schema version history and no safe path for a destructive schema change.
- **Known limitation — one entity relation is inconsistent with its siblings.** `DataDrivenRunEntity.scenario` has no `@JsonIgnoreProperties` trimming, unlike the otherwise-identical `TestRunEntity.scenario` (`10-DATABASE.md` §1.5, §1.3). `DashboardService.getAllRuns()` works around this with flat DTOs, but any *other* future endpoint that serializes a raw `DataDrivenRunEntity` in a list would embed the full scenario, including every recorded step, per row.
- **Not verified**: whether `ApiCollectionService.deleteFolder(...)` correctly reassigns or deletes a non-empty folder's requests before deleting the folder itself — `ApiFolderEntity` has no `@OneToMany` back-reference and no cascade on that side of the relation (`10-DATABASE.md` §1.10).

## Recording

- **Known limitation — recording captures a fixed, narrow set of DOM events.** Only `click`, `change`, `input` (on INPUT/TEXTAREA/SELECT), and `keydown` (Enter only, non-repeat) are listened for (`05-RECORDING-ENGINE.md` §2). **Not captured at all**: mouse movement/hover, drag-and-drop, right-click/context-menu, scroll, file uploads, and every keyboard key other than Enter.
- **Known limitation — no live step list during recording.** The Recording Workspace's "Recorded Steps" panel is a static placeholder; its own text states real-time streaming is not implemented (`03-FRONTEND-FLOWS.md` §5c, `05-RECORDING-ENGINE.md` §1). The user only sees a polled JPEG screenshot (1.5s) and a polled current-URL string (2s) while recording.
- **Known limitation — a fresh recording tears down any prior browser session.** `BrowserManager.resetAndGetBlankPage()` always tears down the existing Playwright session first (`05-RECORDING-ENGINE.md` §1), and refuses to do so entirely while a playback is in progress (throws `IllegalStateException` → HTTP 409). Only one live session — recording, playback, or reset — can exist at a time, application-wide.
- **Known limitation — no scroll/hover capture, but playback compensates partially for hover.** `PlaybackEngine.executeAction` has both a `"scroll"` branch and a `revealViaAncestorHover` fallback (`06-PLAYBACK-ENGINE.md` §6, §8), but nothing in the recorder can ever *produce* a `"scroll"` step, and hover-reveal at playback time is a best-effort compensation for a gap in recording, not a full substitute for it — a genuinely hover-only interaction (no click ever follows) still cannot be recorded.

## Playback

- **Known limitation — two independently-written per-step execution loops.** `PlaybackEngine.runScenario` (standard playback) and `executeSingleStepInternal` (data-driven) share only lower-level helpers, not the outer loop (`06-PLAYBACK-ENGINE.md` §9, `04-UI-AUTOMATION.md` §9). They have already drifted once: `runScenario` has a dedicated up-front MFA check that `executeSingleStepInternal` lacks (MFA pausing there only happens indirectly, after a locator-resolution failure). **Potential risk:** a future fix applied to one path's outer loop will not automatically apply to the other.
- **Known limitation — `HEALED_BY_AI` does not mean an LLM was used.** The status fires for any successful self-healing fallback, including fully deterministic ones (testId, id, name, label matches) — most "AI healed" steps involve zero LLM calls (`06-PLAYBACK-ENGINE.md` §7). A report or dashboard count of "AI healed steps" overstates actual LLM usage.
- **Known limitation — genuine LLM self-healing is off by default.** `mini.automation.llm.api-key` is blank in the committed configuration; without it, `AiElementResolver`'s LLM tier is skipped entirely, logging "No LLM API key configured" (`15-CONFIGURATION.md` §5, `06-PLAYBACK-ENGINE.md` §7). Self-healing still runs, but only through its deterministic strategies (testId/id/name/label/role) — an element that changed in a way none of those five signals can recover from will fail without an LLM key configured.
- **Known limitation — self-healing depends entirely on recorded metadata quality.** Every strategy in `AiElementResolver`'s chain reads from fields captured at recording time (`06-PLAYBACK-ENGINE.md` §7). A step recorded with blank text, no label, no id, and no ARIA role has nothing for any strategy — deterministic or LLM — to work from.
- **Known limitation — CAPTCHA and MFA both hard-block for up to 5 minutes waiting for a human.** By design (`06-PLAYBACK-ENGINE.md` §5) — there is no timeout-and-continue option, and an unattended data-driven run's between-row reset replay explicitly disables MFA pausing for exactly this reason (it would otherwise hang unattended for 5 minutes per reset on any URL drift).
- **Known limitation — no visible browser window means Accessibility scans can never hit an MFA/CAPTCHA wall gracefully.** Accessibility scanning runs headless with no CAPTCHA/MFA detection at all (it is a different execution engine entirely — `08-ACCESSIBILITY.md`, `00-START-HERE.md`). A target URL that requires login will simply scan whatever the login/landing page shows.

## Dynamic websites

- **Known limitation — selector self-healing only triggers when a selector matches zero elements.** If the primary CSS selector matches ≥1 element, it is always accepted, even if the matched element is momentarily invisible or mid-animation — self-healing is not consulted (`06-PLAYBACK-ENGINE.md` §2). A page that renders a *different but selector-compatible* element after a redesign (same tag/class, different meaning) would be silently misclicked rather than healed, because the primary selector still "matches."
- **Known limitation — dropdown/overlay detection is a fixed, hardcoded selector list.** `isDropdownOverlayOpen`/`isInsideDropdownOverlay` recognize a specific set of PrimeNG/ARIA/flatpickr/daterangepicker class and tag patterns (`06-PLAYBACK-ENGINE.md` §8). A custom dropdown widget outside this list gets none of the special overlay-aware timing/retry behavior.
- **Fixed, same session — the frontend's dropdown-classification logic had fallen behind the backend's.** `DataDrivenPanel.tsx`'s hand-copied mirror of `FieldMappingService`'s selector-shape and context-lookup logic was missing two fixes the backend gained earlier this session (unhyphenated PrimeNG tag patterns; immediate-predecessor-only context lookup) — see `07-DATA-DRIVEN.md` §4.6 and `03-FRONTEND-FLOWS.md` §6 for the full mechanism. Both fixes have now been applied to the frontend copy and verified with a clean `tsc -b --noEmit`. **Residual risk, not a current bug**: nothing structurally prevents these two files from drifting again on a future change — there is no shared code or generation step keeping them in sync, only the paired comments in each file. Confirmed by direct line-by-line comparison of both files, both before and after the fix.
- **Known limitation — dropdown-override retry recovery is capped at one reopen attempt.** The retry-with-reopen mechanism (`06-PLAYBACK-ENGINE.md` §4) tries exactly once more after reopening; a site with a genuinely slow or flaky option-list render could still exceed two total attempts.

## Data Driven

- **Known limitation** (restated from "Dynamic websites" above, since it is squarely a Data-Driven-feature-facing gap): the frontend's Field Mapping candidate-detection logic is out of sync with the backend's. See above.
- **Known limitation — no incremental persistence during a run.** As noted under Database: `DataDrivenAsyncExecutor` saves the whole run (all row results) in a single call at the very end (`10-DATABASE.md` §3.1). A crash mid-run leaves nothing in the database for that run at all.
- **Known limitation — reset-between-rows is heuristic, not guaranteed.** `tryResetPageState`'s 5-tier fallback cascade (`07-DATA-DRIVEN.md` §7.4) is entirely generic with no site-specific logic; if every tier fails, the whole run aborts rather than risk executing a row against an unprimed session — this is the correct safety behavior, but it means a sufficiently unusual site can stop a multi-row run partway through with no row-level recovery.
- **Not verified**: whether `DataDrivenRunEntity.dryRun` is ever actually set to `true` by any code path (`07-DATA-DRIVEN.md` §12) — the field exists but no setter call was found.

## Accessibility

- **Known limitation — single-page, single-load scan only.** No crawling; testing a whole site means creating one scan per page (`08-ACCESSIBILITY.md` §4).
- **Known limitation — no interaction simulation.** The page is never clicked, focused, tabbed through, or otherwise driven beyond the initial navigation + settle wait. Anything only reachable after a user action (a modal, a second form step, content behind a click) is never scanned (`08-ACCESSIBILITY.md` §4). This is the explicit, stated reason the Manual/Guided Testing Checklist feature exists.
- **Known limitation — no assistive-technology simulation.** axe-core can confirm an `alt` attribute exists; it cannot judge whether its wording is meaningful, and no real screen reader is ever operated (`08-ACCESSIBILITY.md` §4).
- **Known limitation — the manual checklist's item definitions are frontend-only, not backend-validated.** The 10 checklist items live in a static frontend TypeScript array; the backend only ever stores the tester's free-text answers keyed by item id, with no knowledge of what the items even are (`08-ACCESSIBILITY.md` §7). Changing the checklist content requires only a frontend deploy, with no versioning of which checklist version a given saved answer set corresponds to.
- **Fixed, same session — Accessibility runs were excluded from the main Dashboard's aggregate stats.** `DashboardService.getSummary()` had `AccessibilityScanRunRepository` injected but never queried it, though `getAllRuns()` (Execution History) already included them correctly (`13-DASHBOARD-HISTORY.md` §5). It was unintentional — the repository was clearly meant to be used (it was already injected in the constructor). `getSummary()` now folds Accessibility runs into `totalRuns`/`passedRuns`/`failedRuns`/`successRatePercent`/`recentActivity` (treating status `COMPLETED` as this run type's pass-equivalent, since Accessibility runs never use `PASSED`), with 2 new regression tests in `DashboardServiceTest.java`. **Still open**: `Dashboard.tsx` itself still doesn't visually render most of what `getSummary()` computes, and separately never renders `apiRuns` from `getAllRuns()` in any chart — see the two limitations below.
- **Not verified**: whether any scan-config edit or scan/run deletion capability exists anywhere (`08-ACCESSIBILITY.md` §10) — none was found in `AccessibilityController`.
- **Not verified**: whether `AsyncConfig.DD_TASK_EXECUTOR`'s thread pool sharing between Data-Driven and Accessibility async execution is a deliberate design decision or incidental reuse of the only executor bean available (`08-ACCESSIBILITY.md` §6).

## API Testing

- **Known limitation — a request with zero configured assertions is always reported PASSED, if any HTTP response was received.** `Stream.allMatch` on an empty assertion-result list is vacuously true (`09-API-TESTING.md` §5). A user who sends a request without adding any assertion gets a green "PASSED" regardless of the actual status code.
- **Known limitation — auth resolution has an inconsistent blank-value guard across types.** `BEARER` only sets its header when the resolved token is non-blank; `BASIC` sets its header unconditionally, even with both username and password blank (`09-API-TESTING.md` §4). A misconfigured Basic-auth request silently sends `Authorization: Basic <base64 of ":">` rather than omitting the header.
- **Known limitation — a failed variable extraction is silently skipped, never surfaced as a failure.** `extractValue()`'s failure path logs to stdout and returns `null`; the rule simply contributes nothing, and the request/run is not marked failed because of it (`09-API-TESTING.md` §6). A broken JSONPath in an extraction rule (as opposed to an assertion) fails silently.
- **Known limitation — Postman and OpenAPI import are explicitly partial-fidelity.** No pre-request/test JavaScript import (by design — this app has no arbitrary-JS extension point), nested Postman folders are flattened to one level, OpenAPI import is JSON-only (no YAML), only `servers[0]` is used, only `application/json` bodies import a schema-derived placeholder (`09-API-TESTING.md` §9).
- **Known limitation — error-type classification is string-matching on exception messages, not a structured error code.** `ApiHttpExecutor.classifyError` (`09-API-TESTING.md` §2, `14-ERROR-HANDLING.md` §2) depends on Playwright's exception text staying consistent; a Playwright/JDK upgrade that changes exception wording could silently reclassify an error type.
- **Not verified**: whether `ApiRequestRunResultEntity.status`'s documented `SKIPPED` value is ever actually assigned by any current code path (`09-API-TESTING.md` §1) — no setter call was found for it.
- **Not verified**: whether `RequestEditorTabs.tsx`'s `QUICK_ASSERTIONS` array (the "5 quick" one-click UX shortcuts) is still accurate relative to the engine's actual 13 supported types — not re-read in this documentation pass (`09-API-TESTING.md` §13).

## PDF / Email

- **Known limitation — there is no "download PDF" feature.** The only way to obtain a PDF is to email it to yourself; PDF bytes are never returned to the browser and never persisted to disk (`12-REPORT-PDF-EMAIL.md` §1). A PDF is generated fresh on every "Email Report" click and discarded after the send.
- **Known limitation — email is entirely disabled without configuration, by design, but the failure only surfaces per-click.** With `MINI_AUTOMATION_MAIL_HOST`/`_USERNAME`/`_PASSWORD` unset, every "Email Report" attempt throws `ReportEmailDeliveryException` (`12-REPORT-PDF-EMAIL.md` §5.2) — a clear, intentional failure, but there is no upfront UI indication (e.g. a disabled button, a banner) that email is unconfigured before the user tries to use it.
- **Known limitation — only one font weight is embedded.** No bold `.ttf` is bundled; CSS `font-weight:700` renders as browser/renderer-synthesized bold only (`12-REPORT-PDF-EMAIL.md` §4.2).
- **Known limitation — `word-break:break-all` is unsupported by the PDF rendering engine (openhtmltopdf).** Long unbroken strings (e.g. a resolved API URL with no `/`/`?` characters) can overflow the page width in a generated PDF (`12-REPORT-PDF-EMAIL.md` §4.3).
- **Known limitation — Standard-run PDFs get a "Technical Reference" raw-selector appendix; Data-Driven and API Testing report PDFs do not** (`12-REPORT-PDF-EMAIL.md` §4.5). Whether this is intentional is not stated in source.
- **Known limitation — no test exercises the `API_TESTING` email-send branch by name**, though the branch is structurally identical to the other three and the PDF layer for it is tested (`12-REPORT-PDF-EMAIL.md` §7). A test-coverage gap, not a known functional bug.
- **Known limitation — WCAG Conformance Summary explicitly covers only WCAG 2.0/2.1 Level A and AA, and states in its own generated output that it is not an official VPAT/ACR filing** (`08-ACCESSIBILITY.md` §12, `12-REPORT-PDF-EMAIL.md` §4.6) — by design, not a gap, but worth stating plainly here since the feature name ("Conformance Summary") could otherwise be read as more authoritative than it claims to be.

## Frontend

- **Known limitation — no automated frontend tests exist at all.** No test runner configured, no test files anywhere (`16-TESTING.md` §1, `15-CONFIGURATION.md` §9). All frontend verification in this codebase's history has been manual, live-browser click-through.
- **Known limitation — the backend base URL is hardcoded independently in 4 separate frontend service files**, with no environment variable and no Vite dev-server proxy (`15-CONFIGURATION.md` §9, `02-ARCHITECTURE.md`). Pointing the frontend at a different backend host/port requires editing all four files.
- **Known limitation — frontend TypeScript types are hand-mirrored from backend DTOs/entities, with no code generation.** `types/index.ts` has no OpenAPI/schema-driven generation (`02-ARCHITECTURE.md`, `01-PROJECT-STRUCTURE.md`). A backend response-shape change requires a manual, matching frontend edit, and the two can silently drift — the `DataDrivenPanel.tsx` mapping-logic divergence documented above is a concrete instance of exactly this class of risk, though in matching *logic* rather than a type shape.
- **Known limitation — no global error boundary or Axios interceptor.** Every page repeats its own `try/catch` + `showToast(err?.response?.data?.error ...)` pattern (27 occurrences across 11 files, `14-ERROR-HANDLING.md` §5). A 400, a 409, and a 500 all render as an identical red toast with no status-specific handling.
- **Known limitation — no server-side pagination or filtering for Execution History.** The entire run history across all four execution kinds is fetched in a single request on every page load; all filtering/sorting/search happens client-side over that one already-fetched array (`13-DASHBOARD-HISTORY.md` §10). **Potential risk:** this will not scale gracefully as run history grows, given there is also no database index to make a future server-side query fast either.
- **Known limitation — most of the Dashboard's own backend-computed summary data is fetched but never rendered.** `DashboardService.getSummary()` computes `recordedTests`, `draftTests`, `totalRuns`, `passedRuns`, `failedRuns`, `runningRuns`, `successRatePercent`, and a `recentActivity` feed on every request; `Dashboard.tsx` reads only `totalTests` from that response (`13-DASHBOARD-HISTORY.md` §6). Everything else the Dashboard visually shows is instead computed client-side from a separate endpoint's data.
- **Known limitation — the Dashboard page's own analytics (Total Executions, both donut charts, the 7-day trend) silently exclude API Testing runs**, even though the same already-fetched response includes them and Execution History correctly includes them (`13-DASHBOARD-HISTORY.md` §9, `03-FRONTEND-FLOWS.md` §4).
- **Known limitation — two backend-complete features have no frontend entry point at all.** The Crawler module (`GET /api/crawler/scan`) and Playwright script export's raw-`fetch` caller are each reachable only via direct HTTP call or an existing narrow UI path — Crawler specifically has zero frontend callers anywhere (`00-START-HERE.md`, `11-API-ENDPOINTS.md` §7).

## Configuration

- **Known limitation — several async executors share one small, fixed thread pool with no override.** `AsyncConfig.ddTaskExecutor` (2 core / 4 max / 50 queue) backs `TestRunAsyncExecutor`, `DataDrivenAsyncExecutor`, `ApiRunAsyncExecutor`, and (per `08-ACCESSIBILITY.md`, not independently re-verified in `15-CONFIGURATION.md`) `AccessibilityScanAsyncExecutor` — not configurable via properties or environment variable (`15-CONFIGURATION.md` §7). **Potential risk:** under concurrent load across multiple features at once, background runs could queue behind each other with no visibility into queue depth (no metrics endpoint exposes it — only `health`/`info` are opened via actuator).
- **Known limitation — browser launch flags are hardcoded, not configurable.** Headless-off, 50ms slowmo, and the `--disable-gpu`/`--disable-gpu-compositing` flicker-mitigation args are all fixed in `BrowserManager.java` with no properties/env override (`15-CONFIGURATION.md` §8).
- **Not verified**: whether Accessibility scanning's or API Testing's own isolated Playwright sessions share any of `BrowserManager`'s launch options, or configure their own independently (`15-CONFIGURATION.md` §8, §11).
- **Not verified**: any CI/CD pipeline configuration — no `.github/workflows/` or equivalent was found under a standard path during this documentation survey; a `ci-tools/` directory exists at the repo root but was not opened during round 1 (`15-CONFIGURATION.md`, `16-TESTING.md`). See `23-ARCHITECTURE-HISTORY.md` for what `ci-tools/accessibility-gate.js` specifically is confirmed to do.
- **Not verified**: production deployment configuration (Docker, systemd, reverse proxy, TLS termination) — no such files were found during the round-1 survey.
