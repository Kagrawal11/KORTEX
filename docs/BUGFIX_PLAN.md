> **Follow-up (validated against a real run's logs):** after the above landed, a real recording+playback run against `gmsuat.cgtmse.in` was captured and analyzed. It confirmed the core threading fix works — 18/20 steps executed and passed, versus the browser previously opening and doing nothing at all. Two step failures in that run led to two further, narrowly-scoped fixes in `playback/PlaybackEngine.java`, both **unrelated to the data-driven/threading work above** — pre-existing bugs only now visible because playback actually executes steps:
> 1. **`isInsideDropdownOverlay()`'s ancestor-class check was over-broad.** Bare substring matches like `cls.includes('dropdown')` and `cls.includes('p-multiselect')` match a PrimeNG component's *closed trigger wrapper* (e.g. `class="p-dropdown"`) just as readily as its *open overlay panel* — so clicking an ordinary, unobstructed dropdown trigger was misclassified as "inside an overlay" and force-clicked, which the log evidence indicates left the panel not reliably opening (the very next step's option selector never appeared in the DOM at all, even after an 8s wait). Fixed by requiring panel/open-state-specific class substrings (`dropdown-panel`, `dropdown-item`, `multiselect-panel`, etc.) instead of bare component-name substrings, and dropping `role="combobox"` from the match (that role belongs on the trigger, not overlay content).
> 2. **Delayed/async navigation could be missed by the single before/after URL snapshot.** Both `runScenario()`'s main loop and `executeSingleStepWithOverride()` decide whether to apply the long post-navigation stability wait by comparing the page URL immediately before and immediately after an action — but a click that triggers an async operation (e.g. a login POST that only redirects once its response arrives) can navigate *slightly after* that check runs, so the step wrongly took the short 800ms wait while the page was still transitioning, and the next step then hunted for its target on a not-yet-stable page. Fixed by adding a cheap second URL check after the short wait in both places: if the URL has changed anyway, retroactively apply the same extended stability wait an immediately-detected navigation would have gotten.
> 3. Also added: diagnostic logging for a previously-silent DOM-click failure, and a `dispatchEvent('click')` last-resort fallback after force-click also fails, in the standard click cascade.
>
> **Second follow-up — the flagged gaps, now addressed:**
> 1. **Hover-reveal menus** — rather than adding hover-event capture to the recorder (a larger, noisier feature: naively recording every `mouseover` as the cursor travels toward a target would flood the event stream, and reliably detecting "this hover meaningfully revealed something" is a real design problem on its own), fixed this on the **playback side** instead: `executeAction()`'s click case now checks `locator.isVisible()` before clicking, and if the resolved target isn't currently visible, calls a new `revealViaAncestorHover()` — it walks up the DOM to the element's ancestors (via `xpath=..`, bounded to 4 levels) and calls Playwright's real `.hover()` on each, outermost first, checking after each one whether the target became visible. Real `.hover()` (not a synthetic dispatched event) is used specifically because it moves the actual mouse and drives the browser's own hover-state engine, so it works for both pure-CSS `:hover` reveals and JS `mouseenter`-driven ones. For the vast majority of steps (target already visible) this adds one cheap `isVisible()` check and nothing else.
> 2. **Native `<select>` dropdowns** — root cause confirmed: `CapturedEvent.tag` (the recorded HTML tag name) was captured during recording but never copied onto the persisted `TestStepEntity`, so playback had no way to distinguish a `<select>` from a text `<input>`. Fixed by: adding a `tag` column to `TestStepEntity` (and to `PlaybackEngine.cloneWithOverride`'s field-copy list, so data-driven overrides carry it too), setting it in `RecordingSession.stopRecording()`'s step-building loop, and adding a `"select".equalsIgnoreCase(step.getTag())` branch in `executeAction()`'s input/change/type case that calls the new `selectDropdownOption()` helper — tries `Locator.selectOption(value)` (matches by the option's `value` attribute, what a `<select>`'s `.value` DOM property and so what was recorded actually reflects) and falls back to matching by visible label text.
> 3. **Frontend/backend `isInputStep` divergence** — investigating gap #1 surfaced a real regression risk from the *first* follow-up's Phase 8 tightening: `DataDrivenPanel.tsx` had its own independent copy of the **old, loose** heuristic (`selector/label/placeholder` merely containing "select"), so the mapping UI could still offer a step for mapping that the now-tightened backend `isInputStep()` would reject with "not an input step in the selected range." Fixed by replacing the frontend's loose check with a direct TS mirror of the backend's `looksLikeDropdownOptionSelector` structural predicate, so both layers now agree on exactly the same set of mappable steps.

> **Third follow-up — real production run against `gmsuat.cgtmse.in`, two more issues found and fixed:**
> 1. **"2-column Excel offered 3 mapping slots."** Root cause: the second follow-up's `looksLikeDropdownOptionSelector` broadening (added to fix native `<select>`-adjacent false negatives) matched bare `li:has-text(...)`/`li[...]` patterns generically — but a **fixed, always-the-same workflow-choice menu item** (e.g. clicking "Cancellation / Surrender" to pick which action to perform) can be recorded with the exact same selector shape as a genuine per-row dropdown OPTION (e.g. the actual cancellation reason). Comparing the two steps' raw recorded JSON found the real distinguishing signal: the genuine option was captured with `role="option"` (real ARIA semantics), while the fixed menu item was captured with `role="li"` (just the tag name — no real role). Fixed in `FieldMappingService.isInputStep()` by checking `role="option"` FIRST (the reliable signal) and narrowing the selector-shape fallback to remove the bare `li[...]`/`li:has-text(...)` patterns that caused the false positive (kept vendor-specific option/item/panel-scoped patterns: `mat-option`, `dropdown-item`, `p-dropdown-item`, `p-multiselect-item`, `listbox`, `option[...]`). Mirrored exactly in `DataDrivenPanel.tsx` (new `isDropdownOptionStep()` helper) so the mapping UI and backend validation agree again. Added a regression test (`clickOnFixedActionMenuItem_isNotInputStep_evenWithLiHasTextSelector`) that locks this exact scenario in.
> 2. **Cascading failure wasting ~9 doomed steps after the browser had already died.** In the same run, the mis-mapped step above caused the data loop to fail on bad/nonexistent search data, then the reset-and-replay-pre-loop path hit a `TargetClosedError` (browser closed) partway through replaying pre-loop — but the replay loop, and the sibling `executeStepRangePreLoop`/`executeStepRangePostLoop` methods, had no critical-failure short-circuit (unlike the per-row data loop, which already got this in the first follow-up), so they kept attempting every remaining step against a dead browser, each one burning a full multi-second locator-resolution timeout before failing identically. Fixed by reusing the existing `isCriticalBrowserFailure()` check in all three places, stopping immediately once the browser/page itself is confirmed gone rather than continuing to hammer it. (The underlying cause of *why* the browser closed mid-replay on this particular run — likely resource pressure from a long-lived, never-closed Chromium session across many repeated runs, or something on the site's own side — was not independently diagnosable from the logs alone and is not claimed to be fixed; this change only stops the pointless cascade once it happens.)

> **Fourth follow-up — row 1 succeeded correctly (confirming the third follow-up's fix worked end-to-end), but the loop still only ran once instead of once per dataset row.** Root cause: `tryResetPageState`'s final-fallback navigation goes to `scenario.getTargetUrl()` (the raw entry URL). On this site, the session cookie persists after login — so navigating back to the raw entry URL between rows didn't show the login form again, it redirected straight past it to the dashboard. The subsequent pre-loop REPLAY then hunted for login-form selectors that were never going to appear, which also confused the MFA/intermediate-screen detector into a needless 30-second pause, before the whole replay failed and the run gave up on row 2 entirely (`Total Rows: 1` despite a 2-row dataset).
>
> Fixed by capturing `page.url()` right after pre-loop succeeds the first time (the real "loop start" page, e.g. the post-login dashboard) and trying a direct navigation back to *that* URL as a new intermediate fallback — after `goBack()`, before the raw-target-URL + login-replay last resort. For a persistent-session site (the common case) this recovers in one direct navigation with no re-login attempt at all; sites that genuinely need re-login each time (session doesn't persist) still fall through to the existing last-resort behavior unchanged. Added a regression test (`reset_triesLoopStartUrlBeforeFullTargetUrlReset`) asserting the loop-start URL is navigated to before the raw target URL. Verified with `mvn test` (46/46 passing).
>
> **Fifth follow-up — the fourth follow-up's fix DID trigger correctly (log showed `Navigating to loop-start page: .../dashboard`), but the site still fell through to the destructive raw-URL fallback and hung again.** Two compounding issues, both fixed:
> 1. **The captured loop-start URL was too generic for this SPA.** `/dashboard` is apparently a top-level route; the actual "Guarantee Search" panel is reached via in-app menu clicks (steps 10-12), not a distinct, directly-reloadable URL — so a raw `page.navigate()` to `/dashboard` doesn't restore that client-side view, and the CGPAN field genuinely isn't there after reload. Fixed by restructuring `tryResetPageState` to, after that navigation attempt, REPLAY pre-loop steps **in place** (no further navigation first) rather than immediately escalating to the old destructive "navigate to raw target URL" fallback. This one replay pass naturally handles both remaining cases: a login-form step harmlessly fails fast if the session is still valid (skipped over), while the trailing navigation-only steps (the menu clicks) get a real chance to succeed from wherever the loop-start-URL navigation left the page. The raw-target-URL fallback is now only tried once more, and only if that in-place replay still didn't reach a reset state.
> 2. **The pre-loop replay was hard-blocking on the MFA-pause detector for up to 5 minutes per failing step.** This is the more serious fix: `resolveLocatorWithMfaSupport()` treats a URL drift or MFA-looking page as a genuine, supervised MFA challenge and waits up to 5 minutes for someone to complete it — appropriate for the *first*, attended pre-loop run, but the between-rows reset replay is fully unattended (nobody is watching a "please enter your OTP" prompt that will never actually appear, since we're already logged in). Added `PlaybackEngine.executeSingleStepForReset()` — a new variant threading an `allowMfaPause` flag down to `resolveLocatorWithMfaSupport()` — used only by the reset replay, which now fails a step fast instead of hard-blocking. This is the direct fix for the observed hang (log showed "elapsed=40s, remaining=259s..." — a single reset attempt burning multiple minutes per failed step).
>
> **Known tradeoff, stated plainly:** if a session genuinely expires mid-run and a fresh login triggers a real MFA/OTP challenge during the reset replay specifically, this change means it will now fail fast rather than wait for someone to complete it. Standard (first-run) pre-loop and post-loop execution are unaffected — they still allow the full MFA-pause wait, since a user may legitimately be supervising that part. Given the confirmed, repeated multi-minute hangs this was causing on every single row-to-row reset, that tradeoff is the right call, but it is a real behavior change worth knowing about, not a strictly-better fix with no downside.

> Verified with `mvn clean compile` + `mvn test` (46/46 passing, both prior regression tests updated for the new `executeSingleStepForReset` call). **Not yet verified against the real `gmsuat.cgtmse.in` site** — this fix is reasoned from the log evidence, not confirmed by an actual re-run.

> **Sixth follow-up — the fifth follow-up's fix worked completely at the mechanics level** (confirmed by a real run: both rows executed with correct, different per-row data, no MFA-pause hang, 18 of 20 pre-loop-replay steps failed fast as expected and 2 succeeded, landing the loop back on its starting page for row 2) — **but the overall run was still reported as FAILED** despite `Rows: 2 Passed: 2 Failed: 0, Pass Rate: 100%`. Root cause, found in `DataDrivenExecutionReport.java`: `isOverallSuccess()` returns `preLoopSuccess && postLoopSuccess && failedRows == 0`, and `replayPreLoopForReset()` was calling the same `report.addPreLoopResult(r)` the REAL, one-time pre-loop run uses — which flips `preLoopSuccess` to `false` on ANY failed step. Since the reset replay deliberately re-attempts every pre-loop step in place (including login-form steps that no longer apply once already logged in, which are *expected* to fail harmlessly), it was flipping `preLoopSuccess` false on essentially every reset between rows — corrupting the run's own pass/fail signal even though the real pre-loop run and every data row had genuinely passed. The "Overall Step Summary: Failed: 10" in the report was this same conflation made visible: 10 harmless reset-replay attempts counted as if they were real test-step failures.
>
> Fixed with a new `DataDrivenExecutionReport.addResetReplayResult()` — still records the step (for debugging visibility, tagged `RESET-REPLAY-PRELOOP:`) but does **not** touch `preLoopSuccess` and does **not** count toward the `totalSteps`/`passedSteps`/`failedSteps` summary, since those are meant to represent the test's own pass/fail signal, not this internal recovery bookkeeping. `replayPreLoopForReset()` now calls this instead of `addPreLoopResult()`. Added a regression test (`resetReplayFailure_doesNotMarkTheWholeRunAsFailed`) asserting `isOverallSuccess()` stays `true` when every row passes even though a reset-replay step fails.
>
> Verified with `mvn clean test` (47/47 passing). **Still not independently verified against the real site** — please re-run and confirm the run now reports `PASSED` (not `FAILED`) when every row succeeds.

> **Seventh follow-up — the sixth follow-up's fix confirmed `PASSED` status correctly, but the user rightly flagged the reset replay as wastefully slow and asked for a real fix, not just a status-reporting patch.** Two complementary, generalizable fixes (no site-specific hardcoding):
> 1. **Fast-fail timeout for the reset replay.** Each of the ~10 predictably-failing pre-loop steps (login form fields that no longer apply once already authenticated) was patiently waiting the FULL `SELECTOR_APPEAR_WAIT_MS` (8 seconds) before giving up — 10 steps × 8s ≈ 80 seconds wasted on *every single reset*, confirmed directly in the logs. Added `SELECTOR_APPEAR_WAIT_MS_FAST` (1.2s) and threaded the existing `allowMfaPause` flag (already `false` only for the unattended reset replay) down into `tryResolveLocator()` to select it — a step that doesn't apply now fails in ~1s instead of 8s, cutting the reset time roughly 6-7x with no behavior change to normal, attended playback (which still gets the full 8s).
> 2. **Per-run learning: stop re-probing steps already confirmed unnecessary.** For datasets with 3+ rows, every reset was re-attempting the SAME ~10 login steps that had *already* failed on a prior reset within the same run — the site's authentication state doesn't change back, so once a step is confirmed not to apply, it never will again for the rest of that run. Added a `Set<Integer> knownUnnecessaryPreLoopSteps`, scoped to a single `executeRun()` call (never persisted, never shared across runs): `replayPreLoopForReset()` now skips any step already in that set outright, and adds a step to it the first time it fails non-critically. On a 2-row dataset (one reset total) this has no visible effect; on a larger dataset it turns "re-probe all N steps on every reset" into "pay the probe cost once, then only replay the steps that actually still apply" for every reset after the first.
>
> Together these directly address the user's own diagnosis ("why does it go through steps that are not included in the loop... do something... so it could directly go to the page... from where the loop should execute for the next row") — the fixes don't eliminate the probe entirely (that would require either hardcoding site-specific navigation logic, which is explicitly out of scope for this generic engine, or a URL precise enough for a raw reload to restore the SPA's client-side view, which was already tried and doesn't work for this site's navigation model), but make it fast and, for multi-row datasets, one-time.
>
> Added a new regression test (`reset_skipsAlreadyConfirmedUnnecessaryPreLoopStepsOnLaterResets`) with a 3-row dataset asserting a step that fails once is never re-attempted on a second reset, while a step that keeps succeeding is. Verified with `mvn clean test` (48/48 passing). **Still not independently verified against the real site** — please re-run and confirm both the reset duration drops substantially and (for a 3+ row dataset) later resets log "Skipped N pre-loop step(s) already known not to apply."

> **Eighth follow-up — a different site (LinkedIn's login page) exposed a bug class in self-healing itself, not in the data-driven/reset machinery: healing resolved to a non-editable element and then hung for Playwright's full 30s default per occurrence (log showed a single field failing after ~30s with 63 internal `fill()` retry attempts).** Root cause, found in `playback/AiElementResolver.java`: strategy 4 (label-text fallback) used `page.getByText(step.getLabelText(), ...)`, which matches **whatever element renders that text** — on a "floating label" input design (the label text is its own `<div>`/`<span>` overlaying the real `<input>`, common on modern sites), that is the label/placeholder element itself, never the input. `AiElementResolver` had no way to know the match wasn't actually fillable, so it returned it as "healed"; `PlaybackEngine`'s fallback `locator.fill(value)` call then had no explicit timeout, so Playwright silently retried "visible, enabled, editable" against a permanently non-editable target for its full default 30 seconds before giving up.
>
> Fixed with two complementary, generic (non-site-specific) changes:
> 1. **`AiElementResolver.java`** — for a typing action (`input`/`change`/`type`/`fill`) only, strategy 4 now tries `page.getByLabel(labelText, ...)` FIRST — Playwright's purpose-built accessible-name resolution, which resolves to the actual **form control** a label describes (via `for=`, a wrapping `<label>`, `aria-labelledby`, or `aria-label`), not just anything that happens to render the same text. Both this and the existing `getByText` fallback are now gated by a new `looksEditable(Locator)` check (evaluates the resolved element's tag/type/`isContentEditable` in-page) before being accepted for a typing action — a match that isn't genuinely fillable is rejected and the method keeps trying the remaining strategies (ultimately returning `null`, an honest failure, rather than a false "healed" success). The same `looksEditable` gate was applied to strategy 5 (role/tag+text) for consistency. **Click-type steps are completely unaffected** — `isTypingAction()` gates all of this off, so click-based self-healing (used by the already-verified CGT flow) goes through the exact same `getByText` path as before, unchanged.
> 2. **`playback/PlaybackEngine.java`** — added an explicit `setTimeout(5_000)` to both the `.fill("")` clear call and the fallback `.fill(value)` call in `executeAction()`'s input/change/type case (previously neither had an explicit timeout, so both inherited Playwright's 30s default). This is defense-in-depth alongside fix 1: even if some other kind of non-editable element slips through in the future, the step now fails in ~5s instead of 30s per occurrence.
>
> Added a new regression test file (`playback/AiElementResolverTest.java`, 4 tests): a typing-action label-text match resolving to a non-editable element is rejected (returns `null`, not a false heal); a `getByLabel` match to a genuine input is accepted; a `getByText` match that happens to already be a genuine input is still accepted as a fallback; a click-action label-text match to a non-editable element is still accepted and the editable check is never even consulted (proving click-healing is untouched). Verified with `mvn clean test` (52/52 passing, zero regressions). **Not yet verified against the real LinkedIn site** — this fix is reasoned from the log evidence (the exact ~30s hang with an editable-only-on-real-input distinction) and Playwright's documented `getByLabel`/`getByText` semantics, not confirmed by an actual re-run.
>
> **Corner cases identified for this bug class** (self-healing resolving to a non-editable/decorative element, or relying on volatile auto-generated attributes):
> - **Contenteditable rich-text editors** (e.g. Gmail-style compose boxes) — handled correctly: `looksEditable()` explicitly checks `el.isContentEditable`.
> - **Non-text `<input>` types** (`checkbox`, `radio`, `button`, `submit`, `reset`, `hidden`, `file`, `image`, `range`, `color`) — explicitly excluded from "editable" by `looksEditable()`, since typing into these is meaningless even though they're real `<input>` elements.
> - **Custom web components wrapping a real `<input>`** (e.g. a design-system `<x-input>` whose actual editable element is nested inside) — `getByLabel`/`getByText` may resolve to the **wrapper**, which `looksEditable()` would then reject (wrapper tag isn't `input`/`textarea`, likely not `isContentEditable`). This is an accepted tradeoff: healing fails cleanly and fast for such cases rather than hanging 30s or typing into the wrong place. Not fixed here — would need shadow-DOM/nested-input traversal, which is more invasive and not evidenced by any real log yet.
> - **Elements inside open Shadow DOM** — not a new limitation; Playwright's locator engine (`getByLabel`/`getByText`/`page.locator`) already pierces open shadow roots natively.
> - **Multiple elements sharing similar/overlapping label text** (e.g. "Password" vs "Confirm Password", or a label's text also appearing in unrelated body copy elsewhere on the page) — `getByLabel` is markedly **safer** here than the old `getByText`-only approach, since it only considers elements with genuine label semantics (not arbitrary text-bearing elements), but a partial-match ambiguity between two similarly-labeled fields is still possible; `.first()` is used (matching the pre-existing code's own convention), so this is a pre-existing ambiguity risk, not one introduced by this fix.
> - **Strict-mode violations (locator resolves to >1 element)** — not an issue here: `getByLabel(...)`/`getByText(...)` themselves don't throw at creation time (Playwright locators are lazy), and `.first()` is always called before use, exactly like the pre-existing `getByText` code did.
> - **No editable candidate found by any strategy** — falls through correctly to the existing "last resort: return `null`" behavior (unchanged), so the caller still treats it as a genuine, honest failure rather than a false "healed" success.
> - **Click-vs-type action gating is the most important corner case to get right** — verified via the dedicated regression test that click-based healing (used throughout the already-verified CGT flow) is completely bypassed by the new editable check, preserving 100% of existing behavior for non-typing actions.
> - **Deliberately deprioritized, not fixed in this round:** React's `useId()`-generated volatile DOM IDs (pattern `«rN»`/`:rN:`) are baked into recorded selectors the same way jQuery-UI's `ui-id-N` pattern already is special-cased in `EventListenerInjector.java` — but React's pattern is NOT currently recognized there. This is a distinct, lower-confidence gap (not evidenced by the LinkedIn log itself) that would require touching the CORE selector-resolution path used by every site's playback, not just the self-healing fallback — judged too high-risk/low-evidence to bundle into this fix. Flagged as a candidate follow-up if a future real run's logs show an unstable-ID-related failure.
>
> **Ninth follow-up — a real re-run against LinkedIn showed the eighth follow-up's fixes DID work (proof in the log: `getByLabel` resolved to the genuine `<input type="email">`, and the fallback `fill()` failed in the new 5s bound, not 30s) — but a further, more specific bug was exposed underneath it, and the previously-deprioritized React-id gap turned out to matter after all.**
>
> 1. **Root cause of the continued failure: `AiElementResolver` still picked blindly among multiple matches.** The call log showed the resolved `<input>` was the *right kind* of element but reported `"element is not visible"` for the full 5s retry window. Corroborating evidence in the same log: `PlaybackEngine`'s own structural-selector resolution hit `"4 elements matched ... using the visible one at index 2"` and `"2 elements matched ... using the visible one at index 1"` on the very same page — i.e. this LinkedIn authwall page genuinely renders duplicate DOM structures (a hidden responsive-layout twin, most likely), and `PlaybackEngine` already has logic to scan multi-matches and prefer the first visible one for structural selectors, but that logic had never been ported into `AiElementResolver`'s `getByLabel`/`getByText`/id/name/role-tag strategies — every one of them still called `.first()` unconditionally. `getByLabel("Email or phone").first()` grabbed the hidden duplicate instead of the real, visible input.
> 2. **Fix:** added a new `pickVisibleCandidate(Locator multi, boolean requireEditable)` helper to `AiElementResolver.java` that scans every match (`.nth(i)` up to `.count()`) and returns the first one that is currently `isVisible()` — and, when the step is a typing action, also passes the existing `looksEditable()` check — falling through to the next healing strategy (or, ultimately, an honest `null`) if nothing qualifies. Replaced every blind `.first()` call in the resolution chain (LLM-suggested selector, id, name, label/getByLabel, getByText, role/tag+text) with this helper, for consistency and because the same multi-match risk applies to all of them, not just the label strategy. This only changes behavior when 2+ elements match the same criterion — the overwhelming common single-match case, and therefore the already-verified CGT click-healing flow, is unaffected in the typical case, and can only be *helped* (never hurt) in the rare multi-match case, since the old behavior of blindly grabbing a possibly-hidden element was never correct to begin with.
> 3. **Secondary fix, addressing the user's "cross-verify recording steps" request:** the same log showed steps 1 and 3 each wasting a full 8000ms waiting for `#«r3»`/`#«r4»` to appear before ever reaching self-healing — these are React `useId()`-style per-page-load-random ids, baked into the primary selector at RECORD time. Extended `EventListenerInjector.java`'s existing `generatedUiId` volatile-id detection (previously only matched jQuery-UI's `ui-id-N`) to also treat guillemet-wrapped (`«r3»`, `«Rsvvriejj35659j6»` — the exact form seen in the log) and colon-wrapped (`:r0:`) ids as volatile, in both places the check exists (the main selector-builder and the ancestor-walk positional fallback). A skipped volatile id now falls through to the same existing name/aria-label/title/placeholder/text-based selector chain jQuery-UI ids already use. **This only benefits future recordings** — it does not retroactively change the already-recorded "jh" scenario used in this log, which will continue to rely on fix 1/2 above via self-healing.
>
> Added 3 new regression tests to `AiElementResolverTest.java` covering the exact scenario from the log: a typing-action label match with the first candidate hidden and the second visible+editable picks the visible one (and never even calls `looksEditable` on the hidden one); the same for a click-action text match; and a case where every `getByLabel` match is hidden, correctly falling through to `getByText`. Added the field to the type and a run-level error banner on the report page; also stopped gating the "Pending"/"Never attempted" row-progress indicator to `status === 'RUNNING'` only, so a stopped-but-incomplete run still visually shows the gap.
>   - **This is the direct cause of "execution history is not getting updated" for data-driven runs.** `TestDetails.tsx`'s "Execution History" tab only ever fetched `uiAutomationApi.getTestRuns()` (standard runs) — `dataDrivenApi.getRunsForScenario()` already existed and the backend was already persisting every data-driven run correctly (confirmed via the controller/service/async-executor), but nothing in this tab ever called it. A data-driven run's own report page (`/data-driven/runs/{id}`) worked fine when navigated to directly right after starting a run — it just never appeared anywhere in the list a user would check afterward. Fixed by fetching both run types and merging them into one date-sorted list with a Type column (Standard / Data-Driven), each row linking to its correct report page.
>
> Added 3 new regression tests to `DataDrivenExecutionServiceTest`: a reset-failure scenario asserting `isAborted()==true`, `expectedTotalRows==2`, `totalRows==1`, and `isOverallSuccess()==false` even though the one row that DID run passed cleanly (this test would have failed against the pre-fix code, which reported such a run as successful); a completed-run counterpart asserting `isAborted()==false`; and a direct test that `loopStateLooksReset()` now waits for a field to attach mid-check rather than giving up on an instant snapshot, asserting the run completes both rows without ever falling through to `goBack`/pre-loop-replay fallbacks. Verified with `mvn clean test` (84/84 passing, zero regressions — 81 prior + 3 new) and `tsc -b` (zero new errors, same 5 pre-existing ones).
>
> **Not yet verified against the real CGT site** — reasoned from the actual run log, not confirmed by a live re-test. **Please restart the backend and reload the frontend before re-testing**, as noted in every prior follow-up (Spring Boot does not hot-reload).
>
> **Eighteenth follow-up — the Seventeenth follow-up's fix DID work (both rows now execute, run correctly reported PASSED) — but the user measured the total run time at ~200 seconds for a 2-row dataset and correctly identified why from the log: time was being spent on pre-loop steps that aren't even part of the loop range.** Log evidence, precise: the single between-rows reset replayed all 9 pre-loop steps; steps 1-7 (login fields, checkbox, sign-in button — genuinely inapplicable once already authenticated) each logged `"Selector never appeared in DOM after 15000ms"` before failing — 7 × 15s ≈ 105 seconds alone, on top of the normal per-row execution time.
>
> **Root cause of the regression:** the Seventeenth follow-up's fix for "reset fails and aborts the run" unified the reset-replay's selector-appear timeout with the full attended 15s budget, reasoning that the existing `knownUnnecessaryPreLoopSteps` memoization already bounds this to a one-time-per-run cost. That reasoning was correct about *frequency* (paid once, not once per row) but wrong about *magnitude* — "once" was still nearly two minutes of pure waste, because the fix addressed the wrong layer: it made EVERY step patient, when only a couple of steps (the navigation clicks, steps 8-9) ever actually needed patience — the 7 login-form steps aren't slow to render, they're simply **never going to be there again**, and no amount of waiting changes that.
>
> **Fix — moved the patience from "per-step, always" to "once per navigation, up front," which is both faster AND more correct:** added `DataDrivenExecutionService.waitForPageSettle()` — a bounded (8s) wait for the page to reach NETWORKIDLE, called once right after each reset navigation (`navigateAndCheckReset`'s `page.navigate(...)`, and `goBack()`), replacing a flat, unconditional `Thread.sleep(1000)` in both places. This directly targets the ACTUAL risk (an Angular SPA still doing post-load async rendering when steps are first checked) at its source, instead of hoping a long per-step timeout happens to cover for it. With the page already given a fair, one-time chance to finish rendering before ANY pre-loop step is checked, a step that's genuinely going to appear should already be there (or very close) by the time it's checked — so the per-step timeout for the reset replay was restored to a short, bounded budget: `PlaybackEngine.SELECTOR_APPEAR_WAIT_MS_RESET = 3_000` (a new, deliberately-named constant — 3s, not the original 1.2s that proved too short, and not the 15s that proved wastefully long).
>
> **Net effect:** the 7 inapplicable pre-loop steps now cost at most 7 × 3s ≈ 21s (once per run) instead of 7 × 15s ≈ 105s, while the genuinely-needed navigation steps (8-9) get a full, dedicated up-front settle window (8s) to render BEFORE they're even checked — addressing the original slow-render risk at its actual source rather than by brute-forcing every step's patience upward.
>
> No behavioral test changes were needed for the settle-wait itself (it's a no-op against the Mockito `Page` mocks already used throughout `DataDrivenExecutionServiceTest`, since `waitForLoadState` is unstubbed there) — verified with `mvn clean test` (84/84 passing, zero regressions; the mocked test suite's own runtime dropped from ~30s to ~16s as a direct side effect of no longer sleeping a real 1000ms per reset attempt in-test).
>
> **Not yet verified against the real CGT site for actual elapsed time** — the ~200s baseline came from the user's own run; the expected new total is roughly the previous per-row execution time plus tens of seconds (not ~115s) for the one reset, but this has not been re-measured against a live run. **Please restart the backend before re-testing.**

## Context

Two bugs were reported in `backend/`:
1. **Playback**: clicking "Run Test" opens/shows the Chromium browser but no clicks/typing actually happen against the target page.
2. **Data-driven**: playback "does not fetch data correctly from Excel," "does not follow the steps properly," and "flow breaks and tests fail."

This plan is based on a full read of the relevant source files (not just summaries) across two independent diagnostic passes, plus direct verification of the most load-bearing files (`BrowserManager.java`, `TestRunEntity.java`, `StepExecutionResult.java`). Existing working code is reused wherever possible — this is a set of targeted, method-level fixes, not a rewrite.

## Root Cause Summary

### Bug Set 1 — "Browser opens but nothing gets automated" (root cause, high confidence)

`browser/BrowserManager.java` is a Spring singleton holding exactly **one** Playwright `Playwright`/`Browser`/`Page` for the whole app (by design — "continuous session" UX, browser never auto-closed). Its own class Javadoc already warns *"If a recording is started while a playback is running, every remaining playback step fails instantly with TargetClosedError"* and marks `playbackActive` `volatile` *"because playback and HTTP request threads differ"* — i.e. the developer knew threads differ, but only guarded against one specific collision, not Playwright's general single-thread-confinement requirement for the underlying `Page`/`Browser` objects.

The actual break:
- `TestScenarioService.runScenario()` (`service/TestScenarioService.java:64-76`) calls `this.executeScenarioAsync(...)` (line 73) — a **self-invocation** of an `@Async`-annotated method (line 82). Self-invocation bypasses Spring's AOP proxy, so `@Async` never takes effect; the method runs **synchronously on the calling Tomcat HTTP thread**.
- `datadriven/DataDrivenService.java` has the **identical** bug at `startRun()` → `this.executeAsync(...)` (line 312) calling its own `@Async` method (line 338) — a developer comment at lines 303-311/327-337 explicitly warns about this exact anti-pattern, immediately followed by committing it anyway.
- `BackendApplication.java:8` has `@EnableAsync` with **no custom `TaskExecutor` bean** anywhere in the codebase (confirmed via repo-wide grep).
- The Playwright session (`BrowserManager.ensureSessionAlive()`, lines 226-239) is lazily created on whatever thread first touches it — typically during an earlier "start recording" HTTP request (thread A). A later "Run Test" request lands on a different Tomcat worker thread (thread B, no guaranteed reuse). `PlaybackEngine.runScenario()` then calls `BrowserManager.startPlayback(url)` → `page.navigate(url)` (`BrowserManager.java:94-101`) on the Page object created on thread A, from thread B — violating Playwright Java's documented thread-confinement rule.
- This `startPlayback()` call sits **outside** `PlaybackEngine`'s per-step try/catch, so if it throws, the exception propagates uncaught straight to `TestScenarioService.executeScenarioAsync()`'s catch block (`TestScenarioService.java:108-112`), which only does `System.out.println` and sets `status=FAILED` — **`TestRunEntity` has no error-message field**, so **zero steps ever execute, zero diagnostics are visible anywhere except a stdout line a user watching the popped-up browser never sees.** Even if the violation instead surfaces mid-loop, the per-step catch (`PlaybackEngine.java:375-382`) fails every step identically and instantly — indistinguishable from "nothing happens" to someone watching the live browser.
- `DataDrivenService.executeAsync()` shares the same defect, so data-driven runs are exposed to the same risk on top of Bug Set 3 below.

### Bug Set 2 — Data-driven: Excel data fetched incorrectly

All in `datadriven/DatasetParser.java`, `cellToString()` (~lines 182-206), XLSX path only (CSV path unaffected):
1. **[HIGH]** Date cells never checked via `DateUtil.isCellDateFormatted(cell)` — dates export as raw serial numbers (e.g. `"45906"`).
2. **[HIGH]** Non-whole numeric cells ≥ 10,000,000 go through `String.valueOf(double)`, which Java renders in scientific notation (e.g. `12345678.55` → `"1.234567855E7"`). (The whole-number path already avoids this via a `(long)` cast — only non-integer values are affected.)
3. **[MEDIUM]** 16+ digit IDs lose precision as `double` (exact only to 2^53).
4. **[MEDIUM]** The formula-evaluation-failure fallback (`catch (Exception e) { return trim(cell.toString()); }`) bypasses the date/whole-number guards entirely, reintroducing bugs 1+2.
5. **[LOW]** Formula error cells (`#REF!`, `#DIV/0!`) silently become `""` — no `case ERROR`.
6. **[LOW]** Header dedup (`.toLowerCase()` only) is looser than `FieldMappingService`'s fuzzy-match normalization (also strips non-alphanumerics) — two headers that pass dedup can still collide during mapping.

### Bug Set 3 — Data-driven: step flow breaks / tests fail mid-run

Spans `datadriven/DataDrivenExecutionService.java`, `playback/PlaybackEngine.java`, `datadriven/FieldMappingService.java`, `datadriven/DataDrivenConfig.java`:
1. **[HIGHEST]** `tryResetPageState()`'s final fallback (`page.navigate(scenario.getTargetUrl())`) does **not** re-run pre-loop steps (e.g. login), which only ever run once for the whole run. If reset falls through to this fallback, the browser lands on the login/home page and **every remaining row fails** — a single reset cascades into total run failure.
2. **[HIGH]** `page.goBack()` can restore a stale bfcache'd form still holding the previous row's data; the "is loop-start selector present" check is satisfied by the stale DOM, so reset is falsely considered successful.
3. **[HIGH]** The reset heuristic checks only the **first** loop step's selector *presence* (not value), and runs unconditionally even after a row that failed partway through.
4. **[HIGH]** `RowStatus.CRITICAL_FAILURE` is **dead code** — `executeLoopRow()` never assigns it, only `SUCCESS`/`FAILED`. The documented "stop the run immediately on critical browser failure" behavior is unreachable; a closed/crashed page just produces ordinary `FAILED` rows for every remaining row instead of failing fast.
5. **[HIGH]** `PlaybackEngine.cloneWithOverride()` (~lines 201-222) silently **replays the originally recorded dropdown option** instead of the row's data whenever (a) the mapped value is blank, or (b) the dropdown's selector doesn't match a narrow PrimeNG-specific pattern (`aria-label` / starts-with `li` / `has-text`) — native `<select>` and other dropdown shapes always replay the recorded choice.
6. **[MEDIUM]** A blank mapped value for a text-input step skips the fill entirely (`PlaybackEngine.java:881`), which can leave the **previous row's** leftover value in the field given the imperfect reset above.
7. **[MEDIUM]** `FieldMappingService.isInputStep()`'s dropdown-click heuristic (~lines 219-241) mis-classifies in both directions (false positives on buttons with "select" in their label; false negatives on real dropdowns without it) — and there is currently **no UI escape hatch** for a false negative (`DataDrivenService.getInputStepsInRange()` filters candidates through this heuristic before they ever reach the mapping screen).
8. **[LOW]** `DataDrivenConfig.ResolvedMapping.stepId` is a primitive `long` (vs. `TestStepEntity.id`'s boxed `Long`), making a `null`-check in `DataDrivenService.validateClientMappings` dead code — a client payload omitting `stepId` silently becomes `0` instead of failing loudly.

**Separately noted (not in scope, flag as follow-up ticket):** native `<select>` dropdowns get recorded as `input`/`change` → collapsed into a `"type"` step, and `PlaybackEngine.executeAction`'s `"type"` case calls `.fill()`/`.pressSequentially()`, which Playwright does not support on `<select>` elements (needs `selectOption()`). This is a pre-existing playback bug independent of data-driven mode; fixing it needs a schema addition (no `tag`/element-type column is currently persisted on `TestStepEntity`) — out of scope here.

## Implementation Plan (Ordered Phases)

**Phase 4 (Excel fixes) is fully independent and can run in parallel with everything else — different file, no merge risk.** Phases 5-9 (data-driven flow) should **not** be manually verified until Phase 1 lands, since cross-thread Playwright violations can otherwise corrupt page state in ways that look identical to the flow bugs being fixed.

### Phase 1 — `BrowserManager` single-thread executor (the structural root fix)
**File:** `backend/src/main/java/com/miniautomation/backend/browser/BrowserManager.java`
- Add a single-thread `ExecutorService` field (named thread, daemon), created once.
- Add `<T> T runOnPlaywrightThread(Callable<T> task)` (+ `void` overload):
  - **Re-entrancy guard is mandatory**: if already running on the pinned thread, execute the task inline — otherwise a task-within-a-task on a single-thread executor deadlocks forever. This is the single highest-risk detail in the whole plan; cover it with a dedicated unit test before considering this phase done.
  - Otherwise `executor.submit(task).get()`, unwrapping `ExecutionException.getCause()` and rethrowing it as its original type — required so `resetAndGetBlankPage()`'s `IllegalStateException` still reaches `GlobalExceptionHandler`'s existing 409 mapping instead of degrading to a generic 500.
- Fix `getPage()` (line 176) to be `synchronized` like every other accessor — currently the one non-synchronized accessor, a latent visibility bug.
- Wrap `BrowserManager`'s own `getOrLaunchPage`, `startPlayback`, `resetAndGetBlankPage`, `navigateTo`, `closeSession` bodies in `runOnPlaywrightThread(...)` (defense-in-depth; safe/no-op-cost when already on the pinned thread).
- **Do not touch**: `beginPlayback()`/`endPlayback()`/`isPlaybackActive()` (plain `volatile boolean`, no Playwright calls, already thread-safe) — keep the `playbackActive` mutex exactly as-is; it becomes a fast, readable 409 layered on top of the executor's correctness guarantee, not a replacement for it.

**Wrap the 6 orchestration entry points** (confirmed via full grep — every `browserManager.*` call site in the app funnels through exactly these 6 methods, so no other file needs to change):

| # | File | Method |
|---|---|---|
| 1 | `service/AutomationService.java` | `startRecording(...)` |
| 2 | `service/AutomationService.java` | `stopRecording()` |
| 3 | `service/AutomationService.java` | `runScenario(TestScenarioEntity)` — covers all of `PlaybackEngine`, `MfaPauseDetector`, `CaptchaPauseDetector`, `AiElementResolver` transitively |

**Files:** `service/TestScenarioService.java`, `datadriven/DataDrivenService.java`
- Extract each `@Async` method into its own bean (exactly what `DataDrivenService`'s own comment already recommends): new `service/TestRunAsyncExecutor.java` (moves `executeScenarioAsync` verbatim) and new `datadriven/DataDrivenAsyncExecutor.java` (moves `executeAsync` verbatim), each still `@Async`.

### Phase 3 — Failure diagnostics (schema)
**Files:** `entity/TestRunEntity.java`, `entity/DataDrivenRunEntity.java`, the two async-executor classes from Phase 2
- Add `@Column(columnDefinition = "TEXT") private String errorMessage;` (+ getter/setter) to both entities (verified: neither currently has any error field).

- For `DataDrivenAsyncExecutor`: also handle the **non-exception** failure path — when pre-loop fails, `DataDrivenExecutionService.executeRun` returns a controlled failure (no exception thrown), so synthesize a summary from the first `FAILED` pre-loop step's error and set it explicitly.

### Phase 4 — Excel parsing fixes (parallel-safe, independent file)
**File:** `datadriven/DatasetParser.java`, inside `cellToString(...)` and two small helpers, plus one line in `validateHeaders`.

| Fix | Approach |
|---|---|
| Dates → serial numbers | Before the whole-number check, add `DateUtil.isCellDateFormatted(cell)` → format via `DateUtil.getLocalDateTime(...)` as `yyyy-MM-dd` (or with time if non-midnight). Document as a fixed default format, not per-destination-field-aware. |

### Phase 5 — `RowStatus.CRITICAL_FAILURE` wiring (do before Phase 6)
**File:** `datadriven/DataDrivenExecutionService.java`, `executeLoopRow(...)`
- After a `FAILED` step result, check `page.isClosed()` and/or a narrow set of known "target closed" exception-message signatures. On match, set `RowStatus.CRITICAL_FAILURE` and stop the row immediately.
- No change needed in the caller loop — its `if (status == CRITICAL_FAILURE) break;` already exists and is correct, just previously unreachable.
- Keep detection **narrow** (page-closed / target-closed signatures only) to avoid false-positive run-aborts on ordinary recoverable failures.

### Phase 6 — Pre-loop replay + reset-heuristic hardening
**File:** `datadriven/DataDrivenExecutionService.java`, `tryResetPageState(...)`
- Extend to check **all** loop-range input steps' current *values* (not just the first selector's *presence*) via a small `isElementValueBlank(Page, TestStepEntity)` helper.
- If the previous row **failed**, skip the cheap "already reset" check and go straight to the strong reset path.
- In the final-fallback branch, immediately re-run `executeStepRangePreLoop(...)` (reuse existing method as-is) after the full navigate, before resuming the row loop. Record this as a distinct marker result (e.g. `actionType = "RESET-REPLAY-PRELOOP"`) attached to the next row rather than merging into the one-time pre-loop report bucket.
- If the replay itself fails, escalate to `CRITICAL_FAILURE` (depends on Phase 5).
- **Document explicitly** (code comment + eventually user-facing copy) that pre-loop steps must be idempotent/repeatable (e.g. login) — a one-time step (e.g. signup) will be incorrectly replayed by this fix; this is a scenario-design constraint, not something the code can auto-detect.

### Phase 7 — Dropdown override + blank-value consistency
**File:** `playback/PlaybackEngine.java`
- `cloneWithOverride(...)`: drop the narrow PrimeNG-only gate; trust the caller's existing `isInputStep()` classification and always rewrite to a text-based selector for any non-blank override on a click step. Extend the existing candidate-selector list (add `mat-option:has-text`, `.dropdown-item:has-text`, `[role='option']:has-text`) rather than hardcoding a new pattern.
- Add `SKIPPED` to `StepExecutionResult.StepStatus` (verified: currently only `PASSED`/`HEALED_BY_AI`/`FAILED` — purely additive, no existing switch/if-chain breaks on an unmatched value since consumers either check specific values or just serialize `.name()`).
- `executeSingleStepWithOverride(...)`: when the step is mapped (`valueOverride != null`) and blank, set `SKIPPED` and return without touching the DOM — uniformly for both fill-type and click/dropdown steps, closing the blank-value inconsistency in one change.

### Phase 8 — `isInputStep` heuristic tightening
**File:** `datadriven/FieldMappingService.java`
- Extract a shared `looksLikeDropdownOptionSelector(String)` predicate, used by both `isInputStep()`'s click-branch and Phase 7's selector-rewrite decision, so the two classification points can't silently diverge.
- Tighten false positives: require non-blank `inputValue` OR a selector matching the shared predicate (not just "contains 'select'").
- Document the remaining false-negative gap (no UI escape hatch today) as a follow-up ticket — touch points if picked up later: `DataDrivenService.getInputStepsInRange`, `DataDrivenController`, frontend mapping screen.

### Phase 9 — `ResolvedMapping.stepId` boxing

- Change `ResolvedMapping.stepId` from `long` → `Long` (+ getter/setter). Leave `FieldMapping.stepId`/`MappingApiDto.stepId` as primitive `long` (server-constructed/outbound-only, never exposed to untrusted client JSON) — smallest correct fix.

## Edge Cases

**Threading (Phase 1):**
- Concurrent recording-start during a running playback: `playbackActive` 409 guard still fires first, before ever reaching the executor — verify explicitly.
- MFA/CAPTCHA pauses occupy the pinned thread for up to 5 minutes; a pure DB read (`GET /runs/{id}`) still works, but any other Playwright-touching request queues behind it rather than corrupting state — a strict improvement over undefined behavior today, but confirm queuing (not fast-fail) is acceptable UX.
- `AiElementResolver`'s LLM HTTP call executes on the pinned thread too — a hung LLM endpoint stalls all browser automation app-wide. Flag as a latency risk, not a correctness bug.
- Re-entrancy must be proven via the unit test below before this phase is considered done.

**Excel (Phase 4):**
- Negative numbers: `BigDecimal.valueOf(d).toPlainString()` handles these natively — add an explicit test.
- Mixed date/number columns: each cell classified independently, degrades gracefully.
- CSV path is entirely unaffected (dates/numbers arrive pre-formatted as text) — don't imply CSV needs the same fix.

**Data-driven flow (Phases 5-8):**
- A mapped value that's literally `"0"` or `"false"` must NOT be treated as blank by the new `SKIPPED` logic — only `null`/empty string. Test explicitly.
- `CRITICAL_FAILURE` detection must stay narrow (page-closed / target-closed signatures) to avoid false-positive run-aborts on ordinary validation-message failures.
- Reset-heuristic hardening must keep the cheap check as the *first* attempt (just stricter — value-blank, not just presence) rather than always taking the expensive fallback path.
- Pre-loop containing a one-time (non-idempotent) step — document as an inherent scenario-design limitation, not auto-detectable.

Covers: pre-loop replay triggers on the fallback-navigate path; reset skipped-vs-attempted based on previous row's success/failure; `CRITICAL_FAILURE` stops the run and skips remaining rows; blank mapped value produces `SKIPPED` not a stale fill/click.
- `playback/PlaybackEngineOverrideTest.java` — Mockito-based. Tests `cloneWithOverride`'s broadened selector rewrite against several dropdown shapes, and the new blank-value `SKIPPED` short-circuit.

**Not realistically unit-testable — manual/exploratory plan instead:**
- The actual cross-thread Playwright violation needs a real Chromium instance and two genuinely different threads. Recommend: (1) a thin `@Tag("browser-integration")` test that records against a small local static-HTML fixture then plays it back, asserting all steps `PASSED`/`HEALED_BY_AI` (excludable from fast CI runs); (2) manual verification — start recording, then separately hit "Run Test," and (before the fix) temporarily log `Thread.currentThread().getName()` at Playwright call sites to directly observe the thread mismatch, then confirm it disappears after the fix; (3) manually confirm the `playbackActive` 409 guard still fires immediately (not a 5-minute hang) when recording-start collides with a running playback.

## Risks / Cautions

- **Re-entrancy/deadlock is the single biggest implementation risk** in Phase 1 — a nested `submit().get()` from the pinned worker thread deadlocks silently forever without the re-entrancy guard. Not optional; test it first.
- **Exception-identity must be preserved** through `runOnPlaywrightThread` or `GlobalExceptionHandler`'s existing `IllegalStateException` → 409 behavior silently regresses to 500, breaking existing frontend error handling.
- **Do not weaken or remove the `playbackActive` mutex** — the executor is a correctness layer underneath it, not a replacement.
- **Schema changes auto-apply via `ddl-auto=update`, no migration tool exists** in this project (confirmed, no Flyway/Liquibase in `pom.xml`). The two new nullable `TEXT` `errorMessage` columns are about as safe as an automatic `ALTER TABLE` gets (additive, nullable, no retyping), but still test against a non-production DB copy first.
- **`StepStatus.SKIPPED` is additive but touches shared aggregation/serialization code** — verify no downstream consumer (including the frontend, if later touched) treats an unrecognized status string as an error.
- **Broadening the dropdown-override rewrite (Phase 7) is still heuristic** — gate it behind "caller already classified this as a mapped input step" (as planned), not selector shape alone, to avoid rewriting a plain button's selector that happens to match the broadened pattern.
- **Excel date-output format (`yyyy-MM-dd`) is a fixed default**, not per-destination-field-aware — a strict improvement over raw serial numbers, but document as a known limitation, not a complete fix.
- **This repo may have a large number of uncommitted changes** from an in-progress restructure (`backend_FIXED_v2/`/top-level `frontend/` → current `backend/`/`frontend_FIXED_v2/frontend/` layout — see `docs/architecture/02_System_Architecture.md`). Recommend committing that consolidation before starting this work, so these fixes land on a clean, reviewable baseline.
